# 设计意图路由机制将静态景区知识与天气 交通等高时效信息解耦处理，



工具调用这块，我用的是 function calling 做的隐式意图路由，不是先跑一个意图分类器。

具体做法是：我把天气实况、交通这些工具注册给模型，每个工具有规范的函数名和描述；模型在生成时自己决定要不要调工具、调哪个、参数填什么。

分流的依据是数据时效性——景区知识是静态的、低频变动的，走 RAG 检索；天气和交通是实时的，落进知识库会立刻过期、更新成本也高，所以必须走实时 API 工具。所以本质上不是把两个模块解耦，而是按数据时效性分了两条通道。

这个方案比显式意图分类好在三点：第一，不用多跑一次分类调用；第二，加一个工具就多一条路由，扩展成本低；

代价有两个：一是路由过程隐式、不好观测，出问题要靠 trace 去查；二是它对工具描述的质量极其敏感，描述含糊模型就会错调或漏调。所以我是把工具描述当成 prompt 来迭代的。


# B 版 · 如果没系统测过 —— 这版同样是加分答案，不要怕说
准确率我没有做系统性的量化，这是我这个项目做得不够的地方。 我是用人工抽检的方式看的——大概看了【50】条对话记录，错调主要集中在两类：一类是用户只给了模糊地点时，模型会漏调天气工具；另一类是同一个问题里既有景点又有实时信息时，偶尔只调一个工具。 如果要补，我会建一个覆盖静态 / 实时 / 混合三类的测试集，把工具选择准确率和参数填对率作为回归指标，每次改工具描述都跑一遍。



# 如何优化

工具漏调这个问题，Anthropic 在工具设计指南里明确列过——agent 会犯四类错误：调错工具、参数调错、调用过少的工具、错误处理返回结果。所以它是已知的问题类别，不是偶发 bug。

官方的优化路径优先级很清楚：

第一，先修工具描述。 官方原话是"写工具描述时，想象你在给团队里一个新同事介绍这个工具"——把你默认带上的上下文全部显式写出来，包括什么时候该用、什么时候不该用。他们的证据是：仅仅精修工具描述，Claude Sonnet 3.5 就在 SWE-bench Verified 上达到 SOTA，错误率大幅下降。

第二，减少重叠工具、加命名空间。 官方说"过多或功能重叠的工具会让 agent 分心"。如果两个工具总是被一起调用，正确做法不是逼模型多调，而是把它们合并成一个工具。

第三，建评测集来量化。 官方的方法是：造真实场景的 query，每条标注"期望调用哪些工具"，跑一遍对比模型实际调了什么——这就是漏调率的算法。注意只标注工具、不标注答案，成本比想象中低。而且官方特别指出，强评测任务本身就应该需要多次工具调用，所以混合意图的 case 必须在评测集里覆盖。

第四，用 CoT 定位根因——让模型在调工具前先输出推理，你就能看到它为什么没想起调这个工具。



我的意图路由是通过 LLM 的 Function Calling 实现的。我在 Agent 上注册了多个工具，每个工具有清晰的 name 和 description。LLM 根据用户问题的语义，自动决定调用哪个工具。

比如用户问景区历史、门票、推荐路线这类问题，LLM 会选择 RAG 检索工具，因为这些是静态知识，知识库里有。用户问天气、交通这类问题，LLM 会选择对应的实时 API 工具，因为这些数据实时变化，不适合放知识库。

我之所以把它叫做'意图路由'，是因为这个设计的核心决策是——把问题按数据时效性分类，静态走 RAG、实时走 API，而不是所有问题都塞进 RAG。这个拆分本身就是一种路由策略。



之所以要把静态知识和实时信息解耦，是因为两者的数据特性完全不同。景区介绍、历史典故这类信息变化很少，适合存在知识库里走 RAG 检索。但天气、交通、客流这类信息每小时都在变，放知识库里会过期，必须走实时 API 拿最新数据。如果不做这个拆分，全走 RAG，用户问'明天下不下雨'会拿到知识库里的过时信息，这是严重的体验问题。
