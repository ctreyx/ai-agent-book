# 在什么场景下你会选 Plan-then-Execute 而不是 ReAct？

## 完美面试回答示范

---

> **ReAct 和 Plan-then-Execute 本质上是两种不同的决策粒度，我从优缺点和适用场景三个层面说。**
>
> ---
>
> ### ReAct
>
> **核心机制**是"思考→行动→观察"的短循环，每一步都基于上一步的结果实时决策。
>
> **优点：**
> - **灵活性强。** 不需要预知完整路径，适合探索性任务——比如排查 Bug、调研类问答，你事先不知道需要几步、走哪条路。
> - **容错性好。** 每步都有观察反馈，走错一步下一步可以立刻修正，不存在"整个计划作废"的风险。
>
> **缺点：**
> - **容易陷入局部循环。** LLM 缺乏全局视角，可能反复调用相同工具、生成相同内容，烧 Token 但不推进任务。所以实践中必须加熔断——我的做法是检测连续相同工具调用和相似输出，超过阈值强制终止。
> - **不可预期、不可审批。** 因为是边想边做，用户和上游系统无法提前知道 Agent 会做什么，在涉及支付、数据修改、权限敏感操作的场景下，这个特性会变成风险。
> - **Token 消耗不可控。** 循环次数完全由 LLM 判断，极端情况下成本会远超预期。
>
> ---
>
> ### Plan-then-Execute
>
> **核心机制**是先让 LLM 生成完整的任务计划（拆成 N 个步骤），再逐步执行，执行过程中可以 Replan。
>
> **优点：**
> - **可靠性更高。** 有全局视角，不容易在局部打转；对于可拆分的多步骤任务，完成率明显优于 ReAct。
> - **可审批、可解释。** 计划生成后可以交给用户确认再执行——这在企业级场景中非常关键，比如"帮我订机票+酒店+报销"，用户希望先看方案再授权执行。
> - **成本可预期。** 步骤数在规划阶段就基本确定，Token 消耗有上界。
>
> **缺点：**
> - **规划质量依赖模型能力。** 如果初始计划拆分不合理，后续执行全部偏离。小模型在这一步的表现明显弱于大模型。
> - **Replan 时容易"失忆"。** 执行到第 4 步发现要改计划时，LLM 可能忘记前 3 步的结果和全局约束。所以我会用 State 记录每一步的输入、输出和全局约束（比如预算上限），Replan 时把这些注入上下文。
> - **灵活性不足。** 对于高度开放、路径不确定的任务（比如"帮我调研 XX 领域的竞品"），强行 Plan 反而限制了探索空间。
>
> ---
>
> ### 我的选型原则
>
> | 维度 | 选 ReAct | 选 Plan-then-Execute |
> |------|----------|----------------------|
> | 任务路径 | 不确定、需要探索 | 可预知、可拆分 |
> | 步骤数 | 少（3 步以内） | 多（4 步以上） |
> | 风险等级 | 低（只读查询） | 高（涉及写操作、支付） |
> | 用户预期 | 要快、要灵活 | 要可控、要先确认 |
>
> 实际项目中我倾向**混合方案**：外层用 Plan 做任务拆解，让用户确认后，每个子任务内部用 ReAct 灵活执行。LangGraph 的子图机制天然支持这种嵌套——外层是一张 Plan 图，每个子节点是一张 ReAct 子图，各自维护自己的 State，同时共享全局 State 里的约束条件。
>
> 回到刚才那个文旅场景："两日游、含鲁迅故里、1500 预算、查天气"——我会选 Plan-then-Execute。因为步骤清晰可拆、有全局预算约束需要全程感知、而且用户大概率希望先看方案再确认。但如果是"帮我研究一下绍兴有什么小众景点"，我会选 ReAct，因为路径完全开放，强行 Plan 反而限制了信息发现。

### 这个回答好在哪——结构拆解

| 层次 | 作用 |
|------|------|
| **先定义本质差异**（决策粒度） | 表明你不是在背概念，而是理解了底层区别 |
| **优缺点成对出现** | 每个优点对应另一种模式的缺点，形成对比记忆 |
| **缺点带解法** | 不只说"会失忆"，同时说"所以我用 State 解决"——展示实战能力 |
| **选型维度表格化** | 面试官一听就知道你有决策框架，不是凭感觉选 |
| **落回具体场景** | 把抽象讨论拉回面试开头的文旅项目，首尾呼应 |
| **给出第三选项（混合方案）** | 超出"二选一"的思维，展示架构视野 |
