# 你前端是怎么处理流式输出的？具体用的 SSE 还是 WebSocket？你封装的时候有没有处理断连重试、token 超长截断这些异常情况？ 


"SSE 异常处理我做了几层：

第一，连接断开的处理。 SSE 本身有自动重连机制，浏览器的 EventSource 断开后会自动尝试重连。但我没用原生 EventSource，用的是 fetch + ReadableStream 来手动解析 SSE 流，因为原生 EventSource 不支持 POST 请求，也不能自定义 header 传 token。所以重连逻辑是我自己写的——前端维护一个 retryCount，断连后最多重试 3 次，每次间隔用指数退避（1s、2s、4s），超过 3 次就展示"网络异常，请重新发送"，并且把已经收到的部分内容保留在界面上，不清空。

第二，后端生成到一半报错。 后端如果中途出错，会发一个特殊的 SSE event，比如 event: error，携带错误信息。前端监听到这个事件后，会在当前消息气泡底部展示一个提示："生成中断，点击重试"，用户点击后带上同一个 messageId 重新请求。这样后端可以根据 messageId 做幂等处理，不会重复计费。

第三，token 超长截断。 后端在流式输出时会计数已输出的 token 数量，快到上限时发一个 event: max_length 的信号，前端收到后在消息末尾展示"内容较长已截断，点击继续生成"，用户点击后把前文摘要作为上下文继续生成下一段。   先把 max_tokens 给足（治本）→ 对话场景用续写兜底（补救）→ 续写时做去重 避免重复内容 和轮数限制不然token消耗大（工程）

第四，前端自身的防御。 我在前端做了一个超时兜底——如果 15 秒内没有收到任何 SSE chunk，就主动断开连接并提示用户重试。因为有些情况不是断连，而是后端卡住了，这时候 SSE 连接还活着但就是没数据过来，用户一直看到光标闪烁很焦虑。

第五，已接收内容的保护。 不管什么异常，已经渲染到界面上的文字不会丢失。我用一个 ref 持续拼接收到的 chunk，同时做了一个简单的本地缓存——每收到 10 个 chunk 就写一次 sessionStorage，这样即使用户误刷新页面，也能恢复上次未完成的对话。"

这段回答的结构拆解
层级	场景	处理方式
1	网络断连	指数退避重试 3 次，保留已有内容
2	后端中途报错	监听 error event，展示"点击重试"
3	token 超长	监听 max_length event，支持"继续生成"
4	后端卡死无响应	15 秒超时主动断开
5	已有内容保护	chunk 拼接 + sessionStorage 定期缓存
额外加分点：你可以主动补一句
"另外有一个细节——我用的是 fetch + ReadableStream 而不是原生 EventSource，核心原因有三个：一是 EventSource 只支持 GET，我需要 POST 发送用户消息体；二是 EventSource 不能自定义 header，我需要带 Authorization；三是 EventSource 的错误处理粒度太粗，拿不到 HTTP 状态码，没法区分 401、429、500 做不同的错误提示。"
