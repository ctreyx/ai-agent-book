# 你的回答点评 + 满分示范


## 二、满分示范（约 2 分钟）

程序员更容易只关注技术指标，Recall 多少、Faithfulness 多少，但忽略了用户真正在意的是什么，公司成本是多少。一个 AI Agent 能不能上线，我会从五个维度做检查，缺一不可。


>



>
> ### 第一条线：安全红线 
>
> 越权拦截、注入防御、敏感信息脱敏必须过攻击题库测试。**效果差用户会抱怨，安全出事公司会上新闻**——这条不过,其他都不用谈。具体标准：攻击题库拦截率、越权阻断率必须 100% 通过门禁。

>
> 评测集必须是**真实用户分布**（真实日志为主，覆盖正常/边界/攻击/闲聊四类），在这个前提下：核心指标过基线（如 Faithfulness、任务完成率）、红线指标相比上版本不退化。**我强调"真实分布"是因为很多项目死在这里——评测集是开发者想象的问题，分数很好看，上线就崩，那个分数只是自我安慰。**



# 第二个维度：成本可控——单次成本有上界

这是公司层面必须关注的问题，而不是工程师为了指标好看就可以无限消耗 Token。

text

上线前必须回答三个问题：

① 单次对话平均成本是多少？
  用户量 × 单次成本 > 公司能承受的范围
  → 不能上线，先做成本优化

② 极端情况下成本上界是多少？
  Agent 死循环 / 用户恶意刷请求
  → 有没有 Token 预算上限？
  → 有没有用户级别限流？

③ 指标和成本的平衡点在哪？

  指标和成本之间要找到平衡点
  不能为了指标好看，结果 Token 消耗把公司拖垮
  这个取舍要在上线前算清楚

>
# 第三个维度：稳定性兜底——出了问题系统不崩
这是我认为最容易被忽视、但最重要的维度。很多程序员只关注指标，但用户真正在意的是：用着用着突然崩了怎么办。


三个必须真实验证通过的场景：

① 降级链路真实验证 
  工具挂了 → 实际触发一次
            看用户看到什么
            是友好提示还是报错页面
  LLM 超时 → 实际触发一次
            降级提示是否正常展示
  整体崩溃 → Checkpoint 恢复是否生效
  降级链路必须真实跑过，不能靠信念

② 回滚能力验证
  记忆快照是否存在？
  失败后能否在 10 分钟内回滚？
  有一个"不能回滚"的风险 → 不能上线

③ 熔断机制验证
  Agent 死循环 → 熔断是否真的触发？
  工具重试失败 → 降级是否真的执行？

核心原则：
  不能让用户在使用过程中遇到崩溃
  出了问题能降级、能回滚、能兜底

 


>
> ### 第四条线：体验底线——用户体感不能让用户有失控感
>
> - 首 Token 延迟达标（流式输出是标配）；
> - 长任务过程透明——"正在查询…"而不是转圈 30 秒；
> - 失败话术需要友好
> 长期记忆增加用户粘性

>
> ### 第五条线：可观测——上线不是终点，是数据采集的起点
>
> 全链路追踪、异常自动上报、bad case 回流机制必须在上线**前**就绪。理由很简单：**AI 产品上线时一定有你没发现的问题，区别在于你是第一时间从日志里发现，还是三天后从客户投诉里发现。** 没有观测能力的上线等于裸奔。

上线后如果出问题：
  你能在 10 分钟内知道是哪个节点的问题吗？

上线前必须有：
  ① 全链路日志
     每个节点的输入 / 输出 / 耗时 / Token 数
  ② 关键指标实时看板
     点赞率 / 点踩率 / P95 延迟 / 工具失败率
  ③ 异常自动告警
     核心指标下跌 → 自动通知
     不等用户投诉才发现
