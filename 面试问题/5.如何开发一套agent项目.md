


# 最开始：需求定义——先回答"要不要做 Agent" ， 很多项目失败的根源是把"能一个 Prompt 解决的问题"包装成了 Agent，白白引入了不确定性和成本。

① 这个任务用「固定流程 + LLM 单次调用」能不能解决？
   → 能 → 不要做 Agent，做一条 Chain 就够了
② 任务路径是否不确定、需要动态决策？
③ 是否需要调外部工具、多步推理？
   → ②③ 都是"是" → 才值得上 Agent


需求定义：用户是谁、核心场景 Top5、成功指标是什么（回答准确率？任务完成率？）
明确的边界清单：Agent 能做什么、不做什么（越权范围提前定义，这是后面护栏的依据）
预算约束：单次会话成本上限、延迟目标（首 Token < 2s 这种）


# 阶段 1：最小闭环——先让整条链路跑通

最朴素的 RAG：固定 chunk、纯向量检索、无精排
2-3 个核心工具（业务最高频的），Function Calling 接入
SSE 流式输出
全链路日志——每次调用的输入、输出、耗时、Token 数全部落库

交付物：一个能跑的 Demo + 第一批真实 bad case


# 阶段 2：建立评测——在优化之前，先有尺子

构建评测集：从阶段 1 的真实日志里挑 50-100 条典型 query：高频正常问题、边界问题、越权攻击、闲聊噪音四类。
确定指标：
质量：Context Recall / Faithfulness（用 Ragas）+ 任务完成率（自定义脚本）
性能：首 Token 延迟、端到端延迟
成本：单次会话平均 Token
跑出基线数字——比如 Recall 0.62，这就是后面所有优化的对照组。
建立 bad case 回流机制：线上失败案例自动进评测集，让它成为活的回归测试。
从此以后，任何改动都要回答一个问题：评测分数变了吗？ 不看感觉，看数字。


# 阶段 3：针对性优化——哪里疼治哪里
拿着评测报告做归因，典型的优化路径（以我文旅项目的真实演进为例）：

检索侧（如果 Recall 低）
text

诊断 → 对症下药：
- 专有名词召回差     → 加 BM25 混合检索（权重实测调优）
- 语义鸿沟           → 条件触发 HyDE（只在首轮分数低于阈值时启用，控成本）
- 召回多但噪声大     → CrossEncoder 精排取 Top3（Top5 实测反而稀释上下文）
- 小 chunk 上下文不足 → Parent-Child 索引
生成侧（如果 Faithfulness 低）
Self-RAG 校验：生成后用 LLM 校验是否忠于检索证据，不过则带着校验意见重新生成
熔断：3 次上限，降级为友好提示
这时才引入 LangGraph
注意——到这一步，我的流程里出现了条件分支（HyDE 触发）、循环（校验重试）、全局状态（校验次数、各环节评分），链式结构撑不住了，这时候迁移到 LangGraph 解决疼点。


# 阶段 4：生产加固——从 Demo 到产品的分水岭
四个维度，每个维度一句原则：

① 安全（原则：假设模型一定会被骗）

输入层：规则 + 轻量模型做注入/越权检测
上下文层：外部内容用分隔标记包裹，声明"是数据不是指令"
权限层（底线）：工具最小权限、参数化查询不让模型拼 SQL、高危操作人工确认
输出层：敏感信息脱敏、域外内容拦截

分级重试
熔断 + 降级链路（工具挂了用缓存兜底）
LangGraph checkpoint：失败从断点恢复
状态数据版本快照，可回滚，不能出现脏数据和应用崩溃


任务级 Token 预算
模型分级：意图识别用轻量模型，核心生成用大模型
我们需要考虑成本，每个问题根据不同类型给不同token上限，每个用户需要有token消耗监控

用户体感，Agent 的体验瓶颈不在界面，在"等待"和"失控感"。
过程透明："正在查询天气…"而不是转圈 30 秒

通过长期记忆，记住用户喜好，这是留存率的核心驱动——用户感觉"它记得我"，粘性完全不同


# 阶段 5：可观测与迭代闭环——上线不是终点而是开始

线上运行
  ↓
全链路追踪（每个节点的输入/输出/耗时/Token，LangSmith 或自建）
  ↓
异常自动上报 → bad case 入库
  ↓
每周归因：是切片问题？提示词问题？模型问题？知识库质量问题？
  ↓
修复 → 过评测集回归 → 灰度 → 全量
  ↓
（循环）

最后

把验证过的链路模块化，为第二个项目复用做准备——一个项目的终点应该是团队资产的起点，所以设计的核心问题是：哪些能力下沉为公共服务，哪些留给业务线自定义。

① 工具注册中心（用 MCP 协议）。 天气、地图、OCR 这类通用工具只写一份，注册为公司内部 MCP Server，各业务线的 Agent 作为 Client 按需接入——维护成本从 O(N) 降到 O(1)。业务专属工具（文旅的票务、政务的办事接口）由业务线自己开发，按平台规范注册，经审核后可选择共享给其他线。

② RAG 流水线模板化。 我在文旅项目验证过的整条链路——混合召回、条件 HyDE、CrossEncoder 精排、Self-RAG 校验——抽象成可配置的标准流水线。业务线只需要：上传自己的知识库 + 调参数（chunk 大小、召回阈值、精排 TopK），不需要重新造链路。
