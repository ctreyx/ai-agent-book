# 🎯 面试场景：MCP 和 Tool 有什么区别？

---

## 💬 这样回答（一句话版）

MCP 和 Tool 本质上解决的是同一个问题——让模型获得与外部世界交互的能力，但它们处在不同的抽象层次。

| 对比维度 | LangChain Tool | MCP |
|---|---|---|
| 架构 | 编译时定义、和应用强绑定 | Client-Server 架构，JSON-RPC 通信 |
| 发现方式 | 代码写死，部署时确定 | 运行时动态发现 |
| 能力范围 | 只有 Tool（可执行函数） | Tools + Resources + Prompts |

核心一句话：**Tool 是实现，MCP 是协议。**

---

## 三个关键认知点

**1. 架构模型。** MCP 是一个 Client-Server 架构——你的 Agent 是 MCP Client，工具提供方是 MCP Server，两者通过标准化的 JSON-RPC 协议通信。这和你在 LangChain 里用 `@tool` 装饰器直接写 Python 函数是完全不同的集成方式。

**2. 运行时发现 vs 编译时定义。** 你在 LangChain 里定义 Tool，是写死在代码里的，部署时就确定了。MCP 的核心能力是运行时动态发现——Client 连上 Server 后，Server 会告诉你"我有哪些工具、每个工具的参数 schema 是什么"，Agent 可以动态加载，不需要改代码重新部署。

**3. MCP 不只是 Tool。** 它定义了三类能力：Tools（可执行操作）、Resources（可读取的数据/文件）、Prompts（预定义的提示词模板），比"暴露工具"范围更大。

## 完美面试回答示范

---

> **MCP 和 Tool 本质上解决的是同一个问题——让模型获得与外部世界交互的能力。但它们处在不同的抽象层次，我从三个维度来说。**
>
> ---
>
> ### 一、它们是什么
>
> **Tool** 是我在代码里直接定义的函数。比如在 LangChain 里用 `@tool` 装饰器写一个 Python 函数，声明好 name、description 和参数 schema，LLM 就能调用它。它是**编译时定义、和应用强绑定**的。
>
> **MCP（Model Context Protocol）** 是 Anthropic 提出的一套开放协议，类比的话就是 USB-C——它不关心你插的是 U 盘还是显示器，只要遵守同一个接口标准就能通信。它是一个 **Client-Server 架构**，Agent 作为 MCP Client，工具提供方作为 MCP Server，两者通过标准化的 JSON-RPC 协议通信。
>
> ---
>
> ### 二、核心区别
>
> | 维度 | LangChain Tool | MCP |
> |------|---------------|-----|
> | **定义方式** | 代码里写死，部署时确定 | Server 端注册，Client **运行时动态发现** |
> | **耦合度** | 和应用强绑定，换项目要复制代码 | 解耦，一个 Server 可以供任意 Client 调用 |
> | **能力范围** | 只有 Tool（可执行函数） | 三类能力：**Tools**（可执行操作）、**Resources**（可读取的数据/文件）、**Prompts**（预定义提示词模板） |
> | **协议标准** | 无统一标准，LangChain、OpenAI、Dify 各有各的定义方式 | 统一协议规范，**跨框架、跨语言** |
> | **适用边界** | 公司内部、单项目 | 跨项目、跨团队、跨公司 |
>
> 其中**运行时动态发现**是最关键的区别——MCP Client 连上 Server 后，Server 会自动告诉你"我有哪些工具、每个工具的参数 schema 是什么"，Agent 可以动态加载新能力，**不需要改代码、不需要重新部署**。而 LangChain Tool 你每加一个工具，就得改代码、重新上线。
>
> ---
>
> ### 三、实际场景怎么选
>
> **用 Tool 的场景：**
> - 涉及公司内部业务逻辑、有隐私数据、不希望暴露给外部的能力。比如我们文旅项目里的知识库检索、内部订单查询，这些不可能开放成公共服务。
>
> **用 MCP 的场景：**
>
> 两个方向——
>
> 1. **对外消费通用能力。** 天气查询、航班查询、地图导航这些通用工具，已经有对应企业暴露了 MCP Server，我的 Agent 直接作为 Client 接入就行，不需要自己写 API 对接代码。类似 12306 提供 MCP 查票、高德提供 MCP 查路线。
>
> 2. **对内跨项目复用。** 这个我感受很深——我们公司有多个 AI 项目，很多 Tool 是重复的，比如天气、地理编码、用户鉴权。现在是每个项目各写一份，改一个逻辑要改 N 个地方。如果建一个公司内部的 MCP Server，把这些通用工具统一注册，各项目作为 Client 接入，**维护成本从 O(N) 降到 O(1)**。
>
> 3. **对外暴露能力。** 如果我们是支付公司，可以把支付能力包装成 MCP Server 暴露出去，其他公司的 Agent 直接接入就能用。就像微信支付 SDK，但面向的是 Agent 而不是 App。
>
> ---
>
> ### 四、我的理解
>
> Tool 和 MCP 不是替代关系，而是**不同层次**的东西。Tool 是实现，MCP 是协议。未来趋势大概率是——**Tool 的实现方式不变，但对外暴露和发现的方式会收敛到 MCP 这样的统一协议上**。就像 HTTP 没有替代你的业务代码，但它统一了通信标准。
>
> 如果让我在现有项目里落地，第一步会先把公司内部的通用工具抽成 MCP Server，解决跨项目重复维护的问题——这个 ROI 最高、风险最低、马上就能做。
