

你说的是**存储层的选型**，但完全没有回答**记忆本身怎么设计**。面试官问的不是"用什么数据库存"，而是"记忆的内容是什么、怎么管理、怎么用"。

### 你的回答相当于

> 面试官问："你怎么设计一个图书馆的藏书管理系统？"
> 你回答："书架用木头的，仓库用铁皮的。"

存储介质只是最底层的事，面试官关心的是上面的**策略层**。

### 面试官想听到的完整设计

**第一层：短期记忆（当前会话内）**

| 方案 | 做法 | 优缺点 |
|------|------|--------|
| **完整历史** | 把所有对话 message 直接塞进 context | 简单，但上下文会爆，成本高 |
| **滑动窗口** | 只保留最近 N 轮对话 | 控制 token 量，但早期信息丢失 |
| **摘要压缩** | 每隔 N 轮让 LLM 把历史总结成一段摘要，替换原始历史 | 省 token，但摘要可能丢细节 |
| **滑动窗口 + 摘要（推荐）** | 最近 3 轮保留原文，更早的压缩成摘要 | 兼顾细节和成本 |

> 医疗场景例子：用户第 1 轮说了"我对青霉素过敏"，第 8 轮问"可以吃阿莫西林吗"——如果你的滑动窗口只保留最近 3 轮，过敏信息就丢了，这可能**出人命**。所以医疗场景下，**关键信息必须提取出来持久化**，不能只靠滑动窗口。

**第二层：长期记忆（跨会话）**

| 类型 | 内容 | 存储方式 |
|------|------|----------|
| **用户画像** | 年龄、性别、过敏史、基础病、用药史 | 结构化存储（SQL） |
| **历史摘要** | 过去每次问诊的核心结论 | 文本存储，可向量化检索 |
| **偏好记忆** | 用户喜欢详细解释 vs 简洁回答 | KV 存储 |

> 关键设计：长期记忆**不是把所有聊天记录存起来**，而是**提取结构化的关键信息**。比如从对话中自动提取：`{过敏药物: ["青霉素"], 基础病: ["高血压"], 当前用药: ["氨氯地平"]}`

**第三层：记忆的检索与注入**

存了不代表会用——每次新对话时，你要：

```
1. 加载短期记忆（当前会话历史/摘要）
2. 检索长期记忆（根据当前问题，从历史中召回相关信息）
3. 合并注入 system prompt 或 context
```

> 长期记忆的检索可以用**向量检索**——这就是为什么有些框架（如 Mem0）把记忆也做成 embedding 存向量库。

**第四层：医疗场景特别要注意的坑**

| 坑 | 说明 |
|----|------|
| **关键信息不能丢** | 过敏史、用药禁忌等必须提取为结构化数据，不能只靠上下文窗口 |
| **记忆幻觉** | 模型可能"记错"之前的对话内容，所以关键信息要**从存储中读取**，不能靠模型自己回忆 |
| **隐私合规** | 医疗对话属于敏感数据，存储需要加密、脱敏、设置过期时间，符合医疗数据法规 |
| **记忆冲突** | 用户上次说"没有过敏"，这次说"对青霉素过敏"——以哪个为准？需要**时间戳 + 更新机制** |

> 💡 面试建议：**记忆问题，面试官考的是设计能力**，不是数据库选型。记住这个框架回答：**"短期记忆怎么管（窗口/摘要）→ 长期记忆存什么（结构化提取）→ 怎么检索注入 → 有什么坑"**，按这四层答就很完整。
