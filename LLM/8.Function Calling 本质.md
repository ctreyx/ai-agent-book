# Function Calling 面试回答（1 分钟版）

---

> **Function Calling 的本质是：让模型在"生成文本"之外，多了一条"输出结构化调用请求"的通道。**
>
> **早期做法**是在 Prompt 里写"如果需要查天气，请输出 `查天气(城市)`"。问题很明显——模型会说一堆废话再拼接结果，格式不稳定，解析全靠正则，容错极差。
>
> **现在的 Function Calling** 有两个关键改进：
>
> 第一，**工具定义通过 API 的 `tools` 参数传入**，底层会转换成模型能理解的格式注入上下文，但走的是专门的通道。
>
> 第二，**模型经过专门微调**，当它判断需要调用工具时，不是在正文里输出，而是输出到独立的 `tool_calls` 字段，格式是结构化 JSON——程序可以直接解析，不需要从自然语言里抠。
>
> **但有一点很关键：模型本身不执行工具。** 完整链路是四步——
>
> ```
> ① 模型决策 → 输出 tool_calls（工具名 + 参数）
> ② 应用代码执行 → 真正调 API / 查数据库
> ③ 结果以 tool_result 角色塞回对话
> ④ 模型基于结果继续生成最终回答
> ```
>
> 这个循环可能跑多轮，直到模型判断不需要再调工具为止。
>
> **工程实践上，我踩过的坑和对应做法：**
>
> - **工具描述必须精准且互斥。** 两个工具描述相似，模型选择准确率会明显下降。功能重叠的直接合并。
> - **description 里要写清楚"什么情况用、什么情况不用"**，最好带 few-shot 示例。
> - **参数用 JSON Schema 严格约束**，我在项目里用 Pydantic 做二次校验，因为模型偶尔会传多余标点或类型错误。
> - **工具数量要控制。** 超过 10 个之后选择准确率会掉，这时候应该考虑工具分组或者引入路由层。
>





Function Calling 的本质
一句话总结：Function Calling 本质上就是一种"结构化输出"的特殊 prompt 工程，模型从头到尾只做了一件事——生成文本。

第一层：没有 Function Calling 之前怎么做？
text

你在 system prompt 里手动写：

"你是一个助手，当用户问天气时，请用以下 JSON 格式回复：
{
  "tool": "get_weather",
  "params": { "city": "用户提到的城市" }
}
不要回复其他内容。"
问题：

LLM 可能不按格式输出（多一句话、少一个引号、字段名写错）
你要自己写正则或 try-catch 解析
不稳定，时灵时不灵
第二层：Function Calling 做了什么？
Function Calling 并不是给 LLM 加了一个新能力，而是做了三件事：

1. 训练阶段：让模型学会输出结构化 JSON
text

OpenAI / 智谱在微调模型时，喂了大量这样的训练数据：

用户：北京明天天气怎么样
助手输出：
{
  "name": "get_weather",
  "arguments": "{\"city\": \"北京\", \"date\": \"明天\"}"
}

模型通过海量这种 (问题 → 结构化JSON) 的数据，
学会了"当用户意图匹配某个工具时，输出对应格式的 JSON"
本质上，模型只是在做"下一个 token 预测"，只不过预测出来的 token 刚好组成了一段 JSON。

2. API 层：把工具定义拼进 prompt
当你调用 API 传入 tools 参数时：

TypeScript

const response = await fetch('https://open.bigmodel.cn/api/paas/v4/chat/completions', {
  body: JSON.stringify({
    model: 'glm-4',
    messages: [{ role: 'user', content: '北京明天天气' }],
    tools: [{
      type: 'function',
      function: {
        name: 'get_weather',
        description: '查询指定城市的天气',
        parameters: {
          type: 'object',
          properties: {
            city: { type: 'string', description: '城市名' },
            date: { type: 'string', description: '日期' }
          },
          required: ['city']
        }
      }
    }]
  })
})
API 服务端实际上把 tools 的定义转换成一段文本，拼接到 system prompt 里，大致等价于：

text

[系统内部拼接的 prompt，用户看不到]

你可以使用以下工具：

工具1：get_weather
描述：查询指定城市的天气
参数：
  - city (string, 必填): 城市名
  - date (string, 可选): 日期

当你需要使用工具时，请输出以下格式：
{"name": "get_weather", "arguments": {"city": "xxx", "date": "xxx"}}
所以 tools 定义本身就是 prompt 的一部分，会消耗 token。工具定义越多越详细，token 消耗越大。

3. 输出层：强制解析为结构化格式
普通 prompt 拼接，模型可能输出：

text

好的，我来帮你查天气：{"tool": "get_weather", "city": "北京"}
多了一句废话，你的 JSON.parse 就炸了。

Function Calling 在模型输出后加了一层结构化约束和解析：

text

模型原始输出的 token 流
    │
    ▼
API 层检测到模型正在输出工具调用格式
    │
    ▼
强制将输出解析为标准的 tool_calls 结构
    │
    ▼
返回给你的不是普通 content，而是：

{
  "choices": [{
    "message": {
      "content": null,         // 注意：content 是空的
      "tool_calls": [{         // 结构化的工具调用
        "id": "call_abc123",
        "type": "function",
        "function": {
          "name": "get_weather",
          "arguments": "{\"city\": \"北京\", \"date\": \"明天\"}"
        }
      }]
    },
    "finish_reason": "tool_calls"  // 停止原因是"需要调工具"
  }]
}
第三层：完整的执行流程
模型自始至终没有执行任何工具，执行者是你的代码。

text

第一轮：
  用户 → "北京明天天气"
  你的代码 → 调 API（带 tools 定义）
  LLM → 输出 tool_calls: get_weather(city="北京")
  ⚠️ 到这里 LLM 的工作结束了，它只是"说"了想调什么

第二轮：
  你的代码 → 看到 tool_calls → 调用真正的天气 API → 拿到结果
  你的代码 → 把结果塞回对话：
    {
      role: "tool",
      tool_call_id: "call_abc123",
      content: "北京明天：晴，28°C，东南风3级"
    }
  你的代码 → 再次调 LLM API

第三轮：
  LLM → 看到工具返回的结果 → 生成自然语言回复：
  "北京明天天气晴朗，气温28°C，东南风3级，适合户外活动。"
text

┌──────┐     ┌──────┐     ┌──────────┐     ┌──────────┐
│ 用户  │────▶│ LLM  │────▶│ 你的代码  │────▶│ 真实工具  │
│      │     │      │     │ (执行者)  │     │ (天气API) │
│      │     │      │     │          │     │          │
│      │◀────│      │◀────│          │◀────│          │
└──────┘     └──────┘     └──────────┘     └──────────┘
              生成JSON       解析JSON         返回结果
              "我想调xx"     真正调用          真实数据
第四层：和普通 prompt 拼接的本质区别
维度	普通 prompt 拼接	Function Calling
工具定义	你自己写在 system prompt	API 帮你拼，格式标准化
输出格式	不保证，可能夹杂自然语言	API 层强制解析为 tool_calls 结构
可靠性	低，经常格式出错	高，模型专门训练过
多工具选择	模型容易选错或格式混乱	模型训练过多工具路由决策
并行调用	很难实现	支持一次返回多个 tool_calls
token 消耗	一样	一样（本质都是拼 prompt）
底层原理	一样	一样（都是文本生成）
所以本质区别不在模型端，而在 API 的输入输出标准化和模型的专项微调。

面试标准回答
"Function Calling 本质上还是文本生成。API 把你定义的 tools 转换成文本拼进 system prompt，模型通过专项微调学会了在匹配到用户意图时输出结构化 JSON 而不是自然语言。API 层再把模型输出强制解析为标准的 tool_calls 结构返回给开发者。

模型自始至终没有真正执行任何工具——它只是'说了'想调什么工具、传什么参数。真正执行工具的是我们的代码，执行完再把结果塞回对话，让模型基于结果生成最终回复。

和普通 prompt 拼接的区别主要在三点：一是模型经过专项训练，输出格式更稳定；二是 API 层做了结构化解析，不会夹杂废话；三是支持多工具并行调用。但底层原理是一样的，都是 prompt + 下一个 token 预测。"
