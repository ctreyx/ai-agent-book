# ReAct 面试回答（2 分钟版）

---

> **ReAct 全称是 Reasoning + Acting，核心思想是让模型在执行任务时，交替进行"推理"和"行动"，形成 Thought → Action → Observation 的循环，直到任务完成。**
>
> ---
>
> ### 一、ReAct 的执行流程
>
> 以用户问"绍兴后天天气怎么样，推荐穿什么"为例：
>
> ```
> Thought 1: 用户问了两件事——天气和穿搭建议。
>            穿搭依赖天气结果，所以我应该先查天气。
> Action 1:  调用天气工具（参数：绍兴，后天）
> Observation 1: 后天 晴 32℃
>
> Thought 2: 已经拿到天气了，32℃ 高温晴天，
>            我可以直接根据这个信息给穿搭建议，不需要再调工具。
> Action 2:  直接生成最终回答
> ```
>
> 每一轮 Thought 决定下一步做什么，Observation 提供反馈修正下一轮 Thought。这个循环让模型具备了**动态纠偏**的能力——走错一步，下一步可以调整。
>
> ---
>
> ### 二、Thought 在工程上是怎么产生的
>
> **Thought 不是模型天生会做的事，是 Prompt 工程驱动的。** 实现方式有两种：
>
> **第一种：文本格式约束。** 在 System Prompt 里规定输出格式必须是 `Thought: → Action: → Observation:`，配合 few-shot 示例教模型按这个模式走。这是 ReAct 论文的经典实现。
>
> **第二种：结构化输出约束。** 要求模型输出 JSON，其中 `thought` 是必填字段：
>
> ```json
> {
>   "thought": "用户问天气，我需要调用天气工具",
>   "action": "weather_tool",
>   "action_input": {"city": "绍兴", "date": "后天"}
> }
> ```
>
> 如果模型输出里缺少 `thought` 字段，代码层面直接拒绝、要求重新生成。
>
> ---
>
> ### 三、为什么 Thought 不能跳过
>
> 这不只是"防止乱调工具"的问题，更深层的原因是：**LLM 是自回归模型，前面生成的 token 直接影响后面 token 的概率分布。** Thought 步骤本质上是给模型一张"草稿纸"——先把推理过程写出来，后续的工具选择和参数传递才会更准确。
>
> 这就是 Chain-of-Thought 的核心原理。没有 Thought，模型的决策质量会显著下降——表现出来就是选错工具、传错参数、遗漏子任务。
>
> ---
>
> ### 四、ReAct 的核心优缺点
>
> **优点：**
> - **灵活。** 不需要预定义执行路径，模型根据每步的 Observation 实时调整策略。适合路径不确定的探索性任务。
> - **可解释。** 每一步的 Thought 都是可审计的，出了问题可以追溯是哪一步推理出了偏差。
>
> **缺点：**
> - **容易陷入死循环。** 模型可能反复调用同一个工具、或者在两个工具之间来回跳，持续消耗 Token 但不推进任务。
> - **Token 消耗不可控。** 循环次数完全由模型决定，极端情况下成本远超预期。
> - **缺乏全局视角。** 每步只看上一步的结果，不像 Plan-then-Execute 那样有完整计划，容易在局部打转。
>
> ---
>
> ### 五、我在实际项目中的防护措施
>
> 针对这些缺点，我做了四层防护：
>
> **第一层：熔断机制。** 设置最大循环次数上限，我的项目里是 10 次。超过直接终止，降级为友好提示。
>
> **第二层：重复检测。** 每轮记录工具名和参数，如果连续两次调用相同工具、传入相同参数，说明模型"迷路"了，立即终止。
>
> **第三层：Thought 校验。** 通过结构化输出要求 `thought` 字段必填。如果模型跳过思考直接调用工具，代码层面拦截并要求重新生成。
>
> **第四层：线上异常追踪。** 所有被熔断或重复检测终止的 case 会自动上报，作为 bad case 进入评测集，驱动后续 Prompt 优化。
>
> ---
>
> ### 六、一句话总结
>
> **ReAct 的核心价值是把 LLM 从"一问一答的生成器"变成了"能观察环境、动态调整策略的执行者"。但灵活性是双刃剑——越灵活越需要工程侧的约束和兜底，否则线上一定会出问题。**
