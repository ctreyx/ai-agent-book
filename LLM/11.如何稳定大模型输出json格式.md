# 工具调用失败有哪几类情况?如何处理非法JSON输出?

原因:
1. 大模型本质是文字接龙，无抽象语法树概念，容易出现 括号等不全问题
2. plhf 副作用，模型过于礼貌，容易出现 好的，数据如下。。  导致下游解析出错
3. token飘逸，长时间注意力分散，导致低权重的标点符号容易丢失。



## 七、面试标准回答

> "工具调用失败我分四类处理。
>
> **第一类，LLM 选错工具。** 预防为主——把工具 description 写得边界清晰不重叠，必要时用 tool_choice 强制指定工具。
>
> **第二类，LLM 生成了非法 JSON。** 我做了三层解析：第一层正则预清洗，去掉 markdown 包裹、自然语言废话、尾部多余逗号等常见脏数据；第二层用 json_repair 库修复更复杂的语法错误；第三层如果前两层都失败了，把错误 JSON 和错误信息反馈给 LLM 让它重新生成。解析成功后再过一遍 Pydantic 做参数类型和值的校验，校验失败也是反馈给 LLM 重新生成。
>
> **第三类，工具执行失败。** 超时和连接错误做指数退避重试，最多 2 次。限流做退避等待。其他错误不重试直接降级，给用户友好提示并记录日志通知运维。
>
> **第四类，工具返回了结果但 LLM 生成的回复有问题。** 这个就是我之前讲的生成质量评估——用另一个 LLM 打分，分数低就重试，3 次上限。
>
> 在 LangGraph 里，这些处理逻辑对应不同的 conditional_edge：全部成功走生成节点，部分成功走降级生成，全部失败走重试或兜底。整个错误处理是状态机的一部分，不是事后打补丁。"

好，这是 Agent 开发岗的高频面试题。我从**故障分类 → 处理策略 → 完整代码 → 面试话术**给你讲清楚。

## 一、工具调用失败的完整分类

```
工具调用的完整链路：

用户输入 → LLM 决定调哪个工具 → LLM 生成参数 → 执行工具 → 拿到结果 → LLM 生成回复
            ①                    ②              ③          ④           ⑤

每一步都可能失败，失败的类型完全不同
```

---

### 第①类：LLM 选错了工具

```
用户问："明天杭州天气怎么样"
LLM 选了：RAG 检索工具（应该选天气 API 工具）

原因：
  - 工具的 description 写得不够清晰，边界模糊
  - 用户问题有歧义
  - 模型能力不足

示例：
  工具A description："查询信息"          ← 太模糊
  工具B description："查询天气信息"       ← 也模糊
  
  LLM 分不清该选哪个
```

### 第②类：LLM 生成了非法的参数 JSON

```
正确的格式：
  {"name": "get_weather", "arguments": {"city": "杭州", "date": "明天"}}

LLM 可能输出的错误格式：

  错误1：JSON 格式不对
  {"name": "get_weather", "arguments": {"city": "杭州",}}
                                                        ↑ 多了逗号

  错误2：夹杂自然语言
  好的，我来查一下天气。{"name": "get_weather", ...}
  ↑ 前面多了废话

  错误3：参数类型错误
  {"name": "get_weather", "arguments": {"city": 123}}
                                                ↑ 应该是字符串

  错误4：缺少必填参数
  {"name": "get_weather", "arguments": {}}
                                        ↑ city 是必填的

  错误5：参数值不合理
  {"name": "get_weather", "arguments": {"city": "地球"}}
                                                 ↑ 不是有效城市

  错误6：幻觉参数——编造了不存在的参数名
  {"name": "get_weather", "arguments": {"location": "杭州"}}
                                         ↑ 参数名应该是 city 不是 location

  错误7：选了不存在的工具
  {"name": "get_traffic", "arguments": {...}}
                ↑ 这个工具根本没注册过
```

### 第③类：工具执行失败

```
LLM 选对了工具，参数也对了，但执行的时候出错：

  错误1：外部 API 超时
  → 天气 API 5 秒没响应

  错误2：外部 API 返回错误
  → 天气 API 返回 500 / 429（限流）/ 403（无权限）

  错误3：外部 API 返回异常数据
  → 天气 API 返回了空数据或格式变了

  错误4：数据库查询失败
  → 知识库连接断了

  错误5：业务逻辑错误
  → 查一个不存在的景区 ID

  错误6：权限不足
  → 这个用户没有权限调用某个工具
```

### 第④类：工具返回结果但 LLM 生成回复失败

```
工具返回了正确结果，但 LLM 在最终生成回复时出错：

  错误1：LLM 忽略了工具返回的结果，自己编了一个答案（幻觉）
  错误2：LLM 曲解了工具返回的数据
  错误3：LLM 生成的回复格式不对（比如你要求 JSON 但它输出了自然语言）
  错误4：LLM API 本身超时或报错
```

## 三、非法 JSON 输出的处理（重点）

### 第一层：正则预清洗

```python
import re
import json


def clean_llm_json(raw_output: str) -> str:
    """清洗 LLM 输出的脏 JSON"""

    text = raw_output.strip()

    # 1. 去掉 markdown 代码块包裹
    #    LLM 经常输出 ```json ... ```
    text = re.sub(r'^```(?:json)?\s*', '', text)
    text = re.sub(r'\s*```$', '', text)

    # 2. 去掉前后的自然语言废话
    #    "好的，我来查一下：{...}" → "{...}"
    json_match = re.search(r'(\{[\s\S]*\})', text)
    if json_match:
        text = json_match.group(1)

    # 3. 修复常见的 JSON 语法错误
    #    尾部多余逗号：{"a": 1,} → {"a": 1}
    text = re.sub(r',\s*([\]}])', r'\1', text)

    # 4. 修复单引号
    #    {'city': '杭州'} → {"city": "杭州"}
    text = text.replace("'", '"')

    # 5. 去掉控制字符
    text = re.sub(r'[\x00-\x1f\x7f]', '', text)

    return text
```

### 第二层：多策略 JSON 解析

```python
def parse_llm_json(raw_output: str) -> dict | None:
    """多策略尝试解析 LLM 输出的 JSON"""

    # 策略1：直接解析（最快）
    try:
        return json.loads(raw_output)
    except json.JSONDecodeError:
        pass

    # 策略2：清洗后解析
    cleaned = clean_llm_json(raw_output)
    try:
        return json.loads(cleaned)
    except json.JSONDecodeError:
        pass

    # 策略3：用 json_repair 库修复
    #   能处理更复杂的错误：
    #   缺少引号、多余字符、截断的 JSON 等
    try:
        from json_repair import repair_json
        repaired = repair_json(raw_output)
        return json.loads(repaired)
    except Exception:
        pass

    # 策略4：用 LLM 修复（最后手段）
    #   把错误的 JSON 再发给 LLM 让它修正
    #   成本高但成功率高
    # try:
    #     fixed = await llm.invoke(f"请修复这段JSON：{raw_output}")
    #     return json.loads(fixed)
    # except:
    #     pass

    # 全部失败
    return None
```

### 第三层：Pydantic 参数校验

```python
from pydantic import BaseModel, Field, validator
from typing import Optional, Literal
from enum import Enum


class WeatherParams(BaseModel):
    """天气查询工具的参数校验"""
    city: str = Field(..., min_length=1, max_length=20, description="城市名")
    date: Optional[str] = Field(default="今天", description="日期")

    @validator('city')
    def validate_city(cls, v):
        # 过滤明显不合理的值
        invalid = ['地球', '宇宙', '世界', '中国']
        if v in invalid:
            raise ValueError(f"'{v}'不是有效的城市名，请提供具体城市")
        return v

    @validator('date')
    def validate_date(cls, v):
        valid_patterns = ['今天', '明天', '后天', '大后天']
        # 也支持 2026-09-15 格式
        if v not in valid_patterns and not re.match(r'\d{4}-\d{2}-\d{2}', v):
            raise ValueError(f"日期格式不正确：{v}")
        return v


class RAGSearchParams(BaseModel):
    """RAG 检索工具的参数校验"""
    query: str = Field(..., min_length=2, max_length=500)
    top_k: Optional[int] = Field(default=5, ge=1, le=20)


class ToolCallParams(BaseModel):
    """工具调用的顶层校验"""
    name: str
    arguments: dict

    @validator('name')
    def validate_tool_name(cls, v):
        valid_tools = ['get_weather', 'rag_search', 'get_traffic', 'plan_route']
        if v not in valid_tools:
            raise ValueError(f"未知工具：{v}，可用工具：{valid_tools}")
        return v


# 工具名 → 参数校验模型的映射
TOOL_PARAM_VALIDATORS = {
    'get_weather': WeatherParams,
    'rag_search': RAGSearchParams,
}
```

### 第四层：完整的工具调用处理器

```python
import asyncio
from typing import Any


class ToolCallHandler:
    """生产级工具调用处理器"""

    def __init__(self, llm, tools: dict):
        self.llm = llm
        self.tools = tools  # {"get_weather": weather_func, ...}
        self.max_retries = 2
        self.timeout = 10  # 秒

    async def handle_tool_call(
        self,
        raw_tool_call: dict | str,
        user_query: str
    ) -> dict:
        """处理一次完整的工具调用"""

        # =============================================
        # 阶段一：解析和校验
        # =============================================

        # 1. 解析 JSON
        if isinstance(raw_tool_call, str):
            parsed = parse_llm_json(raw_tool_call)
            if parsed is None:
                return self._fallback_response(
                    "JSON_PARSE_ERROR",
                    "无法解析工具调用参数",
                    user_query
                )
        else:
            parsed = raw_tool_call

        # 2. 校验工具名
        tool_name = parsed.get("name") or parsed.get("function", {}).get("name")
        if not tool_name or tool_name not in self.tools:
            return self._fallback_response(
                "UNKNOWN_TOOL",
                f"未知工具：{tool_name}",
                user_query
            )

        # 3. 解析 arguments（可能是字符串也可能是 dict）
        arguments = parsed.get("arguments") or parsed.get("function", {}).get("arguments")
        if isinstance(arguments, str):
            arguments = parse_llm_json(arguments)
            if arguments is None:
                return self._fallback_response(
                    "ARGS_PARSE_ERROR",
                    "无法解析工具参数",
                    user_query
                )

        # 4. Pydantic 参数校验
        validator = TOOL_PARAM_VALIDATORS.get(tool_name)
        if validator:
            try:
                validated_args = validator(**arguments)
                arguments = validated_args.dict()
            except Exception as e:
                # 参数校验失败 → 让 LLM 重新生成
                return await self._retry_with_feedback(
                    tool_name,
                    arguments,
                    str(e),
                    user_query
                )

        # =============================================
        # 阶段二：执行工具
        # =============================================

        tool_func = self.tools[tool_name]
        result = await self._execute_with_protection(
            tool_name, tool_func, arguments, user_query
        )

        return result

    async def _execute_with_protection(
        self,
        tool_name: str,
        tool_func,
        arguments: dict,
        user_query: str,
        retry_count: int = 0
    ) -> dict:
        """带超时、重试、熔断的工具执行"""

        try:
            # 超时控制
            result = await asyncio.wait_for(
                tool_func(**arguments),
                timeout=self.timeout
            )

            # 校验返回结果不为空
            if result is None or result == "":
                return self._fallback_response(
                    "EMPTY_RESULT",
                    f"{tool_name} 返回了空结果",
                    user_query
                )

            return {
                "status": "success",
                "tool": tool_name,
                "result": result
            }

        except asyncio.TimeoutError:
            # 超时 → 重试
            if retry_count < self.max_retries:
                await asyncio.sleep(1 * (retry_count + 1))  # 退避
                return await self._execute_with_protection(
                    tool_name, tool_func, arguments,
                    user_query, retry_count + 1
                )
            return self._fallback_response(
                "TIMEOUT",
                f"{tool_name} 连续 {self.max_retries + 1} 次超时",
                user_query
            )

        except ConnectionError:
            # 连接错误 → 重试
            if retry_count < self.max_retries:
                await asyncio.sleep(2 * (retry_count + 1))
                return await self._execute_with_protection(
                    tool_name, tool_func, arguments,
                    user_query, retry_count + 1
                )
            return self._fallback_response(
                "CONNECTION_ERROR",
                f"无法连接到 {tool_name}",
                user_query
            )

        except Exception as e:
            # 其他错误 → 不重试，直接降级
            return self._fallback_response(
                "EXECUTION_ERROR",
                f"{tool_name} 执行失败：{str(e)}",
                user_query
            )

    async def _retry_with_feedback(
        self,
        tool_name: str,
        bad_arguments: dict,
        error_msg: str,
        user_query: str
    ) -> dict:
        """参数校验失败时，让 LLM 重新生成参数"""

        retry_prompt = f"""
你上一次调用工具 {tool_name} 时参数有误。

你生成的参数：{json.dumps(bad_arguments, ensure_ascii=False)}
错误信息：{error_msg}

请根据用户的原始问题重新生成正确的参数。
用户问题：{user_query}

只输出 JSON，不要包含其他内容。
"""
        retry_result = await self.llm.invoke(retry_prompt)
        new_args = parse_llm_json(retry_result)

        if new_args:
            # 再次校验
            validator = TOOL_PARAM_VALIDATORS.get(tool_name)
            try:
                validated = validator(**new_args)
                # 校验通过，执行工具
                return await self._execute_with_protection(
                    tool_name, self.tools[tool_name],
                    validated.dict(), user_query
                )
            except Exception:
                pass

        # 重试也失败了 → 降级
        return self._fallback_response(
            "PARAM_RETRY_FAILED",
            f"多次尝试生成 {tool_name} 参数均失败",
            user_query
        )

    def _fallback_response(
        self,
        error_type: str,
        error_msg: str,
        user_query: str
    ) -> dict:
        """统一的降级处理"""

        # 记录日志（通知运维）
        print(f"[TOOL_ERROR] type={error_type} msg={error_msg} query={user_query}")

        # 根据错误类型给不同的用户提示
        user_messages = {
            "JSON_PARSE_ERROR":    "抱歉，系统处理出现异常，请重新提问",
            "UNKNOWN_TOOL":        "抱歉，暂不支持该功能",
            "ARGS_PARSE_ERROR":    "抱歉，未能理解您的问题，请换个方式提问",
            "TIMEOUT":             "查询服务暂时繁忙，请稍后再试",
            "CONNECTION_ERROR":    "网络连接异常，请稍后再试",
            "EXECUTION_ERROR":     "查询过程中出现错误，请稍后再试",
            "EMPTY_RESULT":        "未查到相关信息",
            "PARAM_RETRY_FAILED":  "抱歉，未能理解您的问题，请换个方式提问",
        }

        return {
            "status": "error",
            "error_type": error_type,
            "error_msg": error_msg,
            "user_message": user_messages.get(error_type, "系统异常，请稍后再试"),
            "original_query": user_query
        }
```

## 四、在 LangGraph 中的集成

```python
from langgraph.graph import StateGraph, END


class AgentState(TypedDict):
    query: str
    tool_calls: list
    tool_results: list
    tool_errors: list
    retry_count: int
    final_answer: str


def tool_executor_node(state: AgentState) -> AgentState:
    """LangGraph 中的工具执行节点"""

    handler = ToolCallHandler(llm, tools)
    results = []
    errors = []

    for tool_call in state["tool_calls"]:
        result = handler.handle_tool_call(tool_call, state["query"])

        if result["status"] == "success":
            results.append(result)
        else:
            errors.append(result)

    return {
        **state,
        "tool_results": results,
        "tool_errors": errors
    }


def should_retry_or_continue(state: AgentState) -> str:
    """条件边：判断工具调用结果"""

    # 全部成功 → 生成回复
    if not state["tool_errors"]:
        return "generate"

    # 有失败但有成功 → 用成功的结果生成回复（降级）
    if state["tool_results"]:
        return "generate_partial"

    # 全部失败且未超重试上限 → 重试
    if state["retry_count"] < 2:
        return "retry"

    # 全部失败且超重试上限 → 降级回复
    return "fallback"


# 构建图
graph = StateGraph(AgentState)
graph.add_node("agent", agent_node)
graph.add_node("tool_executor", tool_executor_node)
graph.add_node("generate", generate_node)
graph.add_node("generate_partial", generate_partial_node)
graph.add_node("fallback", fallback_node)

graph.add_edge("agent", "tool_executor")
graph.add_conditional_edges(
    "tool_executor",
    should_retry_or_continue,
    {
        "generate": "generate",
        "generate_partial": "generate_partial",
        "retry": "agent",        # 重新让 LLM 生成工具调用
        "fallback": "fallback"
    }
)
```

```
流程图：

用户输入
    │
    ▼
  Agent（LLM 决定调哪个工具）
    │
    ▼
  工具执行节点
    │
    ├── 全部成功 ──────────→ 生成回复 → 返回用户
    │
    ├── 部分成功 ──────────→ 用成功的结果生成（告知部分信息暂不可用）
    │
    ├── 全部失败 + 可重试 ──→ 回到 Agent 重新生成工具调用
    │                          （带上错误反馈让 LLM 修正）
    │
    └── 全部失败 + 超上限 ──→ 降级回复（"暂时无法查询，请稍后再试"）
```

## 五、预防手段（比处理更重要）

```
比起"出了错怎么修"，更重要的是"怎么让它少出错"：

1. 工具 description 写得足够清晰
   ❌ "查询信息"
   ✅ "查询指定城市在指定日期的实时天气预报，
      包括温度、降水概率、风力等。
      仅支持中国大陆城市。"

2. 参数 description 要有示例
   ❌ city: "城市"
   ✅ city: "城市名称，如'杭州'、'北京'，不要带'市'字"

3. 用 GLM-4 及以上模型
   低端模型 Function Calling 的 JSON 格式稳定性差很多

4. 工具数量控制在 10 个以内
   工具太多 LLM 选错的概率显著上升

5. tool_choice 参数
   如果某个场景明确只需要某个工具：
   tool_choice = {"type": "function", "function": {"name": "get_weather"}}
   强制 LLM 只调这个工具，消除选错的可能
```

## 六、故障处理总结表

| 故障类型 | 原因 | 处理策略 |
|---------|------|---------|
| 选错工具 | description 不清晰 | 优化描述 + tool_choice 强制 |
| JSON 格式错误 | LLM 输出不稳定 | 正则清洗 → json_repair → LLM 修复 |
| 多余自然语言 | LLM 没遵守指令 | 正则提取 JSON 部分 |
| 参数类型/值错误 | LLM 幻觉 | Pydantic 校验 + 让 LLM 重新生成 |
| 缺少必填参数 | LLM 遗漏 | Pydantic 校验 + 反馈给 LLM |
| 工具不存在 | LLM 幻觉 | 白名单校验 + 返回可用工具列表 |
| API 超时 | 网络/服务端 | 指数退避重试 + 超时降级 |
| API 返回错误 | 服务端异常 | 按状态码分类处理 + 重试 |
| API 限流 | 调用频率过高 | 429 退避 + 队列削峰 |
| 返回空结果 | 数据缺失 | 告知用户 + 记录日志 |
| LLM 忽略工具结果 | 幻觉 | 生成后评估 + 重试 |

---

## 七、面试标准回答

> "工具调用失败我分四类处理。
>
> **第一类，LLM 选错工具。** 预防为主——把工具 description 写得边界清晰不重叠，必要时用 tool_choice 强制指定工具。
>
> **第二类，LLM 生成了非法 JSON。** 我做了三层解析：第一层正则预清洗，去掉 markdown 包裹、自然语言废话、尾部多余逗号等常见脏数据；第二层用 json_repair 库修复更复杂的语法错误；第三层如果前两层都失败了，把错误 JSON 和错误信息反馈给 LLM 让它重新生成。解析成功后再过一遍 Pydantic 做参数类型和值的校验，校验失败也是反馈给 LLM 重新生成。
>
> **第三类，工具执行失败。** 超时和连接错误做指数退避重试，最多 2 次。限流做退避等待。其他错误不重试直接降级，给用户友好提示并记录日志通知运维。
>
> **第四类，工具返回了结果但 LLM 生成的回复有问题。** 这个就是我之前讲的生成质量评估——用另一个 LLM 打分，分数低就重试，3 次上限。
>
> 在 LangGraph 里，这些处理逻辑对应不同的 conditional_edge：全部成功走生成节点，部分成功走降级生成，全部失败走重试或兜底。整个错误处理是状态机的一部分，不是事后打补丁。"
