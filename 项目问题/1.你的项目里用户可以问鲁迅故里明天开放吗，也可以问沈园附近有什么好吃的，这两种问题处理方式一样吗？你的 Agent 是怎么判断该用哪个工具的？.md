### 🎯 满分回答：

> **这两种问题处理方式完全不同，我在 LangGraph 里设计了一个意图路由节点来分发。**
>
> **我的 Agent 把用户问题分为三类意图：**
>
> | 意图类型 | 例子 | 路由目标 |
> |---|---|---|
> | **静态知识** | "鲁迅故里门票多少钱"、"沈园的历史介绍" | RAG 知识库检索 |
> | **实时信息** | "明天绍兴天气怎么样"、"鲁迅故里明天开放吗" | 实时 API 工具 |
> | **行程规划** | "帮我规划两天一夜的绍兴行程" | 综合调用多个工具 |
>
> **路由的实现方式：**
>
> ```python
> # LangGraph 里的路由节点
> def route_intent(state):
>     question = state["question"]
>     
>     route_prompt = """
>     判断用户问题的类型：
>     - "rag"：景点介绍、门票价格、历史文化等固定信息
>     - "tool"：天气预报、交通状况、开放状态等实时信息
>     - "plan"：行程规划、路线推荐等综合需求
>     
>     只输出 rag / tool / plan
>     
>     用户问题：{question}
>     """
>     
>     intent = llm.invoke(route_prompt).content.strip()
>     return {"intent": intent}
> ```
>
> **举这两个例子的具体处理流程：**
>
> ```
> "鲁迅故里明天开放吗"
>   → LLM 判断：涉及"明天"→ 时效信息 → intent = "tool"
>   → 路由到天气/开放状态 API 工具
>   → 工具返回实时数据
>   → LLM 组织语言回答用户
>
> "沈园附近有什么好吃的"
>   → LLM 判断：景点周边信息 → 静态知识 → intent = "rag"
>   → 路由到 RAG 检索知识库
>   → 混合检索 + Reranker 精排
>   → LLM 基于检索结果回答
> ```
>
> **你提到的"查询后 LLM 再判断一次匹配度"，我做的具体实现是：**
>
> ```
> 检索结果经过 Reranker 打分后：
>   分数 > 0.5  → 正常回答
>   分数 0.3-0.5 → 回答 + 提示"信息可能不完整"
>   分数 < 0.3  → 降级到 Web Search 或告知用户信息不足
> ```
>
> **这样设计的好处是：静态知识不会每次都调 API 浪费钱，实时信息不会用过时的训练数据回答。**
