## 第一层：数据工程层

> **"现在的问题是数据入库是一次性的，没有生命周期管理。"**

**重做方案：**

```
现在：
  手动采集 → 切片 → 入库 → 完事

重做：
  数据源层（多源接入）
    ├── 景区官网定时爬虫（每日凌晨触发）
    ├── 景区方推送接口（主动更新）
    └── 人工录入后台（运营维护）
         ↓
  数据清洗层
    ├── 去除页眉页脚噪声
    ├── 表格检测（走 Text2SQL 双通道）
    └── 重复数据去重（MD5 哈希比对）
         ↓
  版本管理层
    ├── 每条数据带 doc_id + version + valid_until
    ├── 新数据 pending 状态 → 验证通过 → active
    └── 旧数据 deprecated 状态 → 检索自动过滤
         ↓
  缺口监控层
    ├── 记录知识库没有命中的问题
    ├── 统计高频缺失词汇
    └── 定期推送给运营补充数据

改进理由：
数据是 RAG 的地基，地基不稳，
上面的检索再怎么优化也是徒劳。
知识库不能是死的，要有自我更新能力。
```

## 第二层：检索层

> **"现在的检索链路是对的，但参数是经验值，缺乏数据驱动的调优机制。"**

**重做方案：**

```
现在的链路（已经不错）：
  HyDE → 混合检索（0.6/0.4）→ Reranker → Top3

重做的改进点：

改进1：切片策略精细化
  现在：RecursiveCharacterTextSplitter 固定 500 字
  重做：按文档类型分策略
    ├── 景点介绍（长文）→ 语义切片（SemanticChunker）
    ├── FAQ 问答对     → 按问答对切，不拆散
    ├── 票价表         → 每行转自然语言，存 SQL
    └── 公告通知       → 按段落切，保留标题

改进2：BM25 权重数据驱动调优
  现在：凭经验设 0.6/0.4
  重做：
    ├── 准备测试集跑不同权重组合
    ├── 文化景点类（专有名词多）→ 调到 0.4/0.6
    ├── 美食体验类（口语化描述）→ 调到 0.7/0.3
    └── 每类场景独立权重，不用全局一刀切

改进3：Reranker 换中文模型
  现在：cross-encoder/ms-marco-MiniLM-L-6-v2（英文）
  重做：BAAI/bge-reranker-v2-m3（中文，效果更好）

改进4：加检索置信度分级
  现在：Reranker Top3 直接喂给 LLM
  重做：
    ├── score > 0.7  → 高置信度 → 直接生成
    ├── score 0.4-0.7 → 中置信度 → 带免责声明
    └── score < 0.4  → 低置信度 → 降级 Web Search
                          ↓
                    记录缺口日志 + 通知运营

改进理由：
检索是 RAG 的核心，宁愿在这一层多花时间，
也不要寄希望于 LLM 生成阶段弥补检索的不足。
烂检索给再好的 LLM 也没用。
```

## 第三层：Agent 编排层

> **"现在是单 Agent 什么都干，职责太重，扩展性差。"**

**重做方案：**

```
现在：
  一个 Agent 负责：
  意图理解 + RAG 检索 + 工具调用 + 行程规划 + 输出生成
  → 逻辑耦合，难以维护

重做：多 Agent 协作架构

  用户输入
      ↓
  ┌─ 路由 Agent（Supervisor）─────────────┐
  │  职责：意图识别 + 任务分发             │
  │  判断：chat / locate / plan / tool    │
  └──────────────┬────────────────────────┘
                 ↓
    ┌────────────┼─────────────┐
    ↓            ↓             ↓
 RAG Agent   工具 Agent    规划 Agent
 职责：       职责：        职责：
 知识检索     天气/交通     行程生成
 来源标注     实时数据      预算分配
 置信评分     API对接       路线优化
    └────────────┼─────────────┘
                 ↓
            输出 Agent
            职责：
            结果合并
            格式校验（Pydantic）
            来源标注
            幻觉自检
                 ↓
            结构化 JSON
            驱动前端渲染

改进理由：
单 Agent 就像让一个全栈工程师同时写前端/后端/运维
效率低、出错难追踪、无法单独扩展某个能力。
拆分后每个 Agent 职责单一，
RAG Agent 不够好 → 只优化 RAG Agent
工具 Agent 超时 → 只优化工具 Agent
互不影响。
```

## 第四层：记忆管理层

> **"现在的会话管理太简单，超过轮数就压缩，没有更精细的记忆策略。"**

**重做方案：**

```
现在：
  对话历史存 PostgreSQL
  超过 8 轮 → LLM 压缩 → 摘要继续用

重做：四层记忆架构

L1 工作记忆（Redis，TTL 30分钟）
  → 当前会话最近 6 条消息
  → 毫秒级读写
  → 会话结束自动过期

L2 情节记忆（PostgreSQL）
  → 完整对话历史持久化
  → 记录 Agent 每步决策日志（可溯源）
  → 支持"上次你说要去鲁迅故里"这类跨会话记忆

L3 语义缓存（Redis Semantic Cache）
  → 相似问题直接命中缓存
  → 不用再跑 RAG + LLM
  → 预计命中率 40%，响应速度提升 10 倍

L4 知识记忆（pgvector）
  → 景点知识向量化存储
  → 和业务数据同一个 PostgreSQL，零运维成本

压缩策略升级：
  现在：超过8轮统一压缩
  重做：
    ├── 简单问答（1-3轮）→ 直接丢弃，不需要保留
    ├── 行程规划（多轮）→ 保留关键决策节点
    └── 用户偏好（跨会话）→ 提取到用户画像表长期保存
       "用户 A 喜欢历史文化，预算中等"
       下次进来直接个性化推荐

改进理由：
记忆管理不只是"存历史"，
而是"在对的时间给 Agent 对的上下文"。
全量历史不是越多越好，精准的上下文才有价值。
```

## 第五层：质量保障层

> **"现在是事后评估，出了问题才知道。应该做到事中监控、事前预防。"**

**重做方案：**

```
三道质量防线：

防线一：事前 → 输入校验
  ├── Prompt 注入检测（防止用户用特殊指令绕过约束）
  ├── 敏感词过滤（政治/暴力/竞品信息）
  └── 意图合规校验（超出文旅范围的问题直接拒绝）

防线二：事中 → 分级校验
  （不是所有回答都需要校验，节省时间和成本）

  高置信度（RAG 命中率高）：
    → 跳过额外校验，直接返回
    → 标注来源：✅ 来自官方知识库

  中置信度（Web Search 兜底）：
    → LLM 校验是否有幻觉
    → 标注来源：⚠️ 来自网络搜索

  低置信度（工具多步调用）：
    → LLM 校验 + 人工审核队列
    → 标注来源：⚠️ 综合信息，请以官方为准

防线三：事后 → 持续监控
  ├── LangSmith 全链路追踪
  │     每次请求完整记录：
  │     改写 Query → 检索文档 → Reranker 分数 → LLM 输出
  │
  ├── RAGAS 自动化评估（每周跑一次）
  │     4个指标低于阈值自动告警
  │     优化前后 A/B 对比
  │
  └── 知识缺口日志
        问题无法回答 → 自动记录
        同一问题超过5次 → 推送给运营补充数据
        形成"用户问题 → 驱动数据完善"的飞轮

改进理由：
现在系统是"做完就上线等用户反馈"
应该是"上线前有测试保障，上线后有实时监控"
把质量做成基础设施，而不是事后打补丁。
```

## 第六层：技术选型层

> **"现在的选型是快速启动的选型，不是生产级的最优选型。"**

**重做方案：**

```
向量库：
  现在：Pinecone（SaaS，数据在海外）
  重做：pgvector（PostgreSQL 扩展）

  改变理由：
  → 国内项目数据合规要求本地化存储
  → 我的项目已经有 PostgreSQL（PostGIS）
  → pgvector 直接装扩展，零额外运维成本
  → 向量检索 + GIS 空间查询 + 业务数据 = 一个库搞定

Reranker：
  现在：cross-encoder/ms-marco-MiniLM-L-6-v2（英文）
  重做：BAAI/bge-reranker-v2-m3（中文）

  改变理由：
  → 绍兴文旅场景全是中文
  → 中文 Reranker 对中文语料打分更准确
  → 改一行代码，效果提升显著

Embedding：
  现在：DashScope text-embedding-v3（API 调用）
  重做：保留 DashScope，但加本地 Embedding 缓存

  改变理由：
  → 每次检索都调 API，有网络延迟和费用
  → 知识库文档的 Embedding 提前算好存起来
  → 只有用户查询时才实时调 API，节省 80% 调用次数

部署架构：
  现在：本地跑
  重做：Docker + docker-compose 容器化

  ├── FastAPI（AI Agent 后端）
  ├── PostgreSQL + pgvector + PostGIS
  ├── Redis（缓存 + 语义缓存）
  └── Nginx（反向代理 + SSE 配置）

  一键部署，环境一致，不再"本地跑得好服务器跑不了"
```

## 第七层：产品交互层

> **"现在 AI 回答是黑盒，用户不知道信息从哪来的，不知道置信度多高。"**

**重做方案：**

```
改进1：回答来源可视化
  现在：直接返回文字
  重做：
    ✅ [来源：鲁迅故里官方介绍] → 绿色标签
    ⚠️ [来源：网络搜索]        → 黄色标签
    ❌ [信息不足，建议咨询官方]  → 红色提示

改进2：置信度可视化
  在回答旁边显示一个置信度条
  高置信度（绿）→ 中置信度（黄）→ 低置信度（红）
  让用户知道该不该相信这个回答

改进3：地图与对话深度联动
  现在：用户说"想看 XX 地点"→ 弹窗询问是否跳转
  重做：
    ├── 对话中提到景点 → 地图自动高亮对应 POI
    ├── 用户点地图上的 POI → 自动在对话框问这个景点
    └── 行程规划完成 → 地图自动绘制最优路线 + 时间轴

改进4：个性化记忆
  第一次：问什么答什么
  重做：
    → 记住用户偏好（历史文化 / 自然风光 / 美食）
    → 记住用户预算区间
    → 下次进来："上次你规划了鲁迅故里，
                 这次要继续探索绍兴吗？"

改进理由：
AI 系统最终服务的是人，
不能只优化技术指标（召回率 0.85），
也要优化用户感知（用户觉得靠谱吗？用着爽吗？）
这两者都做好，才是一个完整的产品。
```
